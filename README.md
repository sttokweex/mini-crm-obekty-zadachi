# Мини-CRM «Объекты и задачи»

React + TypeScript + Vite, Supabase Auth и PostgreSQL. Интерфейс на русском. Секретный ключ Supabase не нужен приложению.

## Запуск

1. Создайте проект Supabase. В **Authentication → Providers → Email** отключите **Allow new users to sign up** (открытую регистрацию). В `supabase/config.toml` она также отключена для локального Supabase.
2. Выполните миграцию [`supabase/migrations/202611060001_init.sql`](supabase/migrations/202611060001_init.sql) в **SQL Editor**. При использовании Supabase CLI можно выполнить `supabase db push`.
3. В **Authentication → Users** вручную создайте минимум 3 пользователей с подтверждённым email: постановщика и двух исполнителей. Триггер автоматически создаст профили с ролью исполнителя.
4. Измените три email в [`supabase/seed_demo.sql`](supabase/seed_demo.sql) и выполните файл в SQL Editor. Скрипт назначит первого пользователя постановщиком и добавит 3 объекта, 5 задач и историю. Запускайте его один раз на пустой базе.
5. Скопируйте `.env.example` в `.env.local`, впишите `VITE_SUPABASE_URL` и **publishable/anon key** из **Project Settings → API**. Не используйте `service_role` или secret key.
6. Выполните `npm ci`, затем `npm run dev`. Для проверки production-сборки после настройки переменных — `npm run build`.

Пошаговая публикация: [`DEPLOY_GITHUB_PAGES.md`](DEPLOY_GITHUB_PAGES.md) или [`DEPLOY_VERCEL.md`](DEPLOY_VERCEL.md). Конфигурации обеих площадок уже включены в репозиторий.

## Структура кода

- `src/App.tsx` — маршруты, состояние сессии и доступные пользователю действия.
- `src/api.ts` — все запросы к Supabase.
- `src/Editor.tsx`, `src/Login.tsx`, `src/TaskViews.tsx` — формы и отображение задач.
- `supabase/migrations` — ограничения доступа и бизнес-правила базы.

## Как устроен доступ

- Все четыре таблицы защищены RLS. Постановщик видит все активные объекты и задачи. Исполнитель видит только назначенные ему задачи и объекты с такими задачами.
- Создавать и менять данные объекта и задачи через API может только постановщик. Исполнитель меняет статус своей задачи через `transition_task`.
- `transition_task` в одной операции проверяет допустимый переход и полномочия, меняет статус и записывает историю. Возврат на доработку требует непустой комментарий. Прямое изменение колонки `status` через API запрещено правами PostgreSQL.
- История доступна на чтение только тем, кто видит задачу. У клиентов нет прав на вставку, изменение или удаление её записей.
- Удаление объектов и задач логическое: они исчезают из приложения, но история остаётся для аудита.
- Роли назначаются администратором через SQL Editor, клиент не может менять свой профиль. `service_role` нигде в приложении не используется.

## Проверка безопасности вручную

После настройки войдите как первый исполнитель: в «Моих задачах» видны только его задачи. Прямой запрос к `tasks` с ID задачи второго исполнителя вернёт пустой результат; попытка `update` чужой задачи не изменит строку. Попытка обновить `status` напрямую получит ошибку прав. Вызов `transition_task` с запрещённым переходом, с чужой задачей или с пустым комментарием при возврате даст ошибку. Вставка/изменение/удаление в `task_history` через клиентский API запрещены.

## Решения и допущения

- Пользователей создаёт администратор; публичной регистрации и интерфейса управления пользователями нет.
- Исполнителем задачи может быть только пользователь с ролью исполнителя. Постановщик может переназначать задачу и редактировать её описание даже после принятия; статус при этом не меняется.
- «Удалить» означает скрыть запись с сохранением истории. Удаление объекта скрывает и его задачи.
- Первое событие истории — создание задачи со статусом «Новая». Изменения названия, описания и исполнителя в историю статусов не входят.
- Комментарий требуется только для возврата на доработку.
